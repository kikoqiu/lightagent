# Web 镜像

Web 服务是 CLI 的**实时网页镜像**：它与 CLI 共享同一个 Agent、同一份会话，
CLI 与网页（可同时多个）都能输入；Agent 的事件通过 **WebSocket** 双向实时同步。

## 启用

在 `config.json` 中设置：

```jsonc
"web": { "host": "127.0.0.1", "port": 8080, "password": "secret", "password_salt": "<32 位十六进制>" }
```

* `port > 0` 即启用。命令行可用 `--web-port N` 临时覆盖、`--no-web` 直接关闭。
* `host` 为监听地址，默认（空/省略）`127.0.0.1` 仅本机；设为 `0.0.0.0` 可对局域网开放（请配合 `password`）。
  命令行可用 `--web-host IP` 覆盖。
* 端口被占用时自动尝试 `port+1`、`port+2` …（最多 +50）；启动横幅会打印实际端口。
* `password` 非空即要求**登录**；`password_salt` 会由程序自动生成（手写 `password` 后启动即可），
  详见[登录与鉴权](#登录与鉴权)。

访问 `http://<host>:<port>/`（默认 `http://127.0.0.1:<port>/`）。

## 登录与鉴权

登录是**页面里的对话框**（不再使用浏览器 Basic 弹窗）。密码本身**不出浏览器**：

1. 页面向 `GET /api/session` 询问「是否需要登录」以及**公开的盐**（`web.password_salt`）；
2. 用户在对话框里输入密码，浏览器用 `sha256(盐 + 密码)` 算出**加盐摘要**，只把摘要发给 `POST /api/login`；
3. 服务端用配置文件里的明文密码算出同样的摘要并比较（常量时间），成功后下发 **HttpOnly 会话 cookie**；
4. 之后页面、`/api/config`、`/api/password` 与 **WebSocket 握手**都靠这个 cookie 通过（没有 `?token=` 之类的东西了）。

* **浏览器保存（记住我）**：勾选 “Stay signed in on this browser” 后
  * 会话 cookie 带 `Max-Age`（30 天，默认 12 小时但关掉浏览器即失效），因此重开浏览器仍然登录；
  * 页面把**加盐摘要**（不是密码）存进 `localStorage`，cookie 丢失时自动静默登录；
    换密码时盐会轮换，旧摘要随即失效并被丢弃（不会重放）。
  * 对话框是标准 `<form>`（`autocomplete="current-password"` + 固定的用户名字段），
    浏览器自带的密码管理器也能保存密码；退出登录（页头 **Sign out**，手机窄屏为离开图标的 36px 按钮）
    会清掉会话与本地摘要。
* **设置/更换密码**：配置编辑器 `web.password` 那一行有 **Set / Remove** 按钮（`POST /api/password`）：
  服务端生成新盐、写入 `config.json` 并**立即生效**（无需重启），其它浏览器的会话会被登出，当前浏览器保持登录。
  **Remove** 传空密码即关闭登录：文件里 `web.password` 变成空字符串（该字段总是写出），
  `web.password_salt` 因空值被移除，不会留下「有盐无密码」的半套凭据。
  也可以直接编辑 `config.json`（写 `password`，程序下次启动自动补 `password_salt`）。
* 防护：连续 5 次错误摘要后按地址锁定（5s、10s…最多 5 分钟，返回 `429`）；写操作（`/api/login`、`/api/logout`、
  `/api/config`、`/api/password`）要求同源（`Origin`/`Sec-Fetch-Site` 校验）。
* **页面脚本顺序**：`auth.js`（会话状态与登录对话框）先于 `app.js` 加载，后者据此决定**是否拨号**：
  配置了密码而本浏览器还没登录时，页面只弹登录对话框，不会去建立一个注定被拒的 WebSocket；
  登录成功后对话框通知页面才建立连接，`Sign out` 则立即断开。
  `app.js` 在**调用时**才读取 `window.AUTH`（`AUTH()` 访问器 + `ensureSession()` 兜底），因此
  `auth.js` 缺失或自身出错时退化为「按无需登录处理」去连（真正的门是服务端的握手校验），而不是整页连不上。
* 页面与静态资源（`/`、`*.css`、`*.js`、`/assets/`）**公开**（不含任何数据，且登录对话框必须先能加载）；
  `/ws`、`/api/config`、`/api/password`、`/api/logout` 都要求会话；`/api/session`、`/api/login` 匿名可访问。

> **安全边界（务必了解）**：服务端按需求在 `config.json` 里**明文保存**密码（摘要由它推导，因此必须持有明文）。
> 摘要是「把密码换成加盐哈希」的传输/存储形态，它**等价于该服务的口令**：在明文 HTTP 下被截获即可重放，
> 所以对局域网开放时请配合反向代理的 TLS，或只在 `127.0.0.1` 上使用。浏览器保存的摘要同理，
> 仅对**本机配置**有效（换密码即失效，换机器无用）。

## 页面文件

前端源码以**普通文件**内嵌（`internal/web/`，`go:embed`），不引入构建步骤、不依赖 CDN：

| 文件 | 说明 |
|------|------|
| `index.html` | 页面骨架（含 viewport、登录对话框、朗读设置对话框与占位符：markdown 开关、工具结果开关、命令表、多媒体附件能力），服务端每次请求替换后再返回 |
| `app.css` | 页面样式（响应式布局、主题、消息行上的复制控件、日志区的悬浮跳转按钮） |
| `app.js` | 页面行为（WebSocket、渲染节奏、输入、左侧命令栏、消息复制菜单、滚动跟随与跳转按钮、隐藏页省电） |
| `auth.js` | 登录对话框：取盐、算加盐摘要（自带 SHA-256，明文 HTTP 下没有 WebCrypto）、保存摘要、连接门控 |
| `config.js` | 配置编辑器（表单 / JSON 两种模式，访问 `/api/config`、`/api/password`）与面板里的**重启**按钮（`/api/restart`） |
| `tts.js` | 朗读面板：语言/语音选择、朗读内容选择（写 `localStorage`，不经服务端），并把对话事件读出来 |
| `math.js` | 公式渲染：把回复里的 `$…$` / `$$…$$` 渲染为 MathML（浏览器自带排版，无 webfont、也无第三方公式库），见[公式（MathML）](#公式mathml) |
| `assets/` | 第三方库（marked / DOMPurify），见该目录的 `README.md` |

`app.css`、`app.js`、`auth.js`、`config.js`、`tts.js`、`math.js` 由 `/app.css`、`/app.js`、`/auth.js`、
`/config.js`、`/tts.js`、`/math.js` 提供，
和页面、`/assets/` 一样**公开**（不含数据）；受保护的只有 `/ws` 与 `/api/*` 中的数据端点，它们靠会话 cookie，
因此子请求不再需要 `?token=`。

页面与内嵌资源（`/`、`*.css`、`*.js`、`/assets/`）都返回 `Cache-Control: no-cache`：
UI 随二进制内嵌，重建后浏览器会重新校验，不会继续使用旧版脚本/样式。

## 配置编辑（`/api/config`）

**入口**：页头右上角的 **⚙**（手机端同样可见），或桌面端侧栏的 “Configuration” 卡片。
面板里对 `config.json` 提供两种编辑模式，右上角的 **Form / JSON** 标签切换：

* **Form（表单）**：按段展开的控件表单，每项一行——左侧是配置键名 + 说明，右侧是控件：
  文本框、密码框、数字框、开关、滑杆（带实时数值）、下拉、多行文本。
  段落为 OpenAI / Context / Web mirror / Tools · shell / Tools · files / Tools · web /
  Tools · discovery / Tools · MCP / Agent / UI（`▸` 可折叠，OpenAI、Context、Web 默认展开）。
  控件改动**立刻写进当前文档**，所以切到 JSON 看到的就是将要提交的内容。
  留空表示“用内置默认”（保存时该项直接从文件中移除）；`extra_body` 与 `tools.mcp.servers`
  是这两个 map 型字段的 JSON 文本框（标有 `json` 标签）。
* **JSON**：整份文档原文编辑，适合复制粘贴或表单没覆盖的场景。切回表单时以文本框内容为准；
  若 JSON 非法，则**留在 JSON 模式**并提示错误，不会丢掉已输入的内容。

**保存前会在两端校验**：

* 客户端：数字项非数字/超范围、JSON 文本框解析失败 → 行内红字 + 该行高亮，**Save 被阻止**并提示
  是哪个字段；
* 服务端：未知字段（拼写错误）、缺少 `openai.api_key`、启用的 MCP server 缺 `command`/`url` 等 → `400`，
  状态行显示服务端原文（未知字段会额外提示去 JSON 模式删除）。

成功保存后状态行显示 `saved — restart lightagent to apply it`。**保存只写文件，运行中的进程继续
使用启动时的配置**，重启 lightagent 后才生效（面板始终提示这一点）；面板底部的 **Restart** 就地把这一步做完：
先保存会话、换进程、自动恢复（见[重启](#重启apirestart)）。

### 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/config` | 读取当前文件（默认值补全、`api_key` 打码） |
| PUT | `/api/config` | 请求体为 JSON 文档；校验后写回文件（也接受 `POST`，便于 curl） |

两者都在与页面相同的鉴权之下（需要登录后的会话 cookie）。响应结构（GET 与 PUT 相同）：

```json
{ "path": "D:\\...\\config.json", "config": { ... }, "pending_restart": false }
```

* 返回的文档已按**启动时的规则**合并默认值（缺失字段显示默认值、`tools.mcp.servers` 会补上占位 server），
  且 `openai.api_key` 与 `web.password` **打码为 `***`**（与 `--print-config` 一致）。保存时若这两个字段为 `***` 或空，
  服务端沿用文件里原有的值，因此改模型等其它字段无需重新输入；要换密钥/密码直接粘贴新值即可
  （新密码会**立即生效**并轮换盐，见[登录与鉴权](#登录与鉴权)）。`web.password_salt` 是公开值，按原样回显
  （为空时不出现）。
* `web.password` 那一行是**密码控件**（`Set` / `Remove` + 状态行），走 `POST /api/password`：
  写入文件并立即生效，不用重启；其余字段仍是「保存后重启生效」。
* 被拒绝时**文件原样保留**；写回的文件一定可以通过启动校验。
* **Reload** 重新从磁盘读取（外部编辑也能显示）；未保存的改动在重新打开面板时仍保留。
* 会话过期时任何请求都会返回 `401`，面板会提示重新登录（页面自动弹出登录对话框）。
* 命令行临时覆盖（`--model`、`--api-base`、`--web-port` 等）只作用于当前进程，不会写回文件。
* 该接口仅在镜像启动时接入了配置文件（正常启动总是如此）时可用，否则返回 `404`。

## 重启（`/api/restart`）

**入口**：配置面板底部的 **Restart**（面板从页头 **⚙** 或桌面侧栏进入，手机端同样可用）。按钮**点两次**才生效：
第一次把它变成 `Confirm restart` 并在状态行说明会发生什么，10 秒不确认自动撤销（跟 Save / Reload 并列，误点不会重启）。

一次重启就是「**保存 → 换进程 → 自动恢复**」三步：

1. **先保存**：接口走与 `/save` 相同的路径把当前会话写进 `session.json`。回合运行中会被拒绝（这一轮的文本还没进历史），
   写盘失败也被拒绝——重启不该丢掉它答应保留的对话。被拒绝时返回 `409` / `500`，进程照常运行。
2. **再换进程**：新进程由**同一个可执行文件**、**同一份命令行**启动，并附加 `--resume`，因此会**自动载入刚保存的会话**
   （不弹出询问），刚写好的 `config.json` 同时生效。`-C/--dir` 不传递（新进程直接继承当前工作目录，避免相对路径被解析两次）、
   `--no-save` 也不传递（重启后的退出仍应保存），其余开关（`-c`、`--model`、`--session`、`--web-port` …）原样保留，
   所以新进程和旧进程是同一个运行配置。
3. **页面自己回来**：旧进程在退出前**交出监听地址**（`ReleaseListener`：只关监听套接字，不关已有连接，所以正在写的这个
   响应照常送达），新进程随后绑定**同一个地址**，页面按既有重连逻辑接回（页头把这段时间显示为 `restarting…` 而不是 `offline`），
   并用完整快照重建日志区——回放的正是刚恢复的那份会话。只有新开标签页的那一刻可能撞上换进程的窗口。

细节：新进程**不是**旧进程的子进程，因此不受退出清理（exec 会话、stdio MCP server）影响；终端在交接前已恢复原状，
终端里会看到新进程重新打印横幅与恢复的历史（`resumed N messages from …`）。
替换进程**起不来**时接口返回 `500`（例如可执行文件缺失），当前进程继续运行、页面原样可用；镜像没有接入重启回调时
（嵌入式使用）接口返回 `501`，页面会直接隐藏该按钮。

## WebSocket 协议

连接 `ws://127.0.0.1:<port>/ws`（需要登录后的会话 cookie，浏览器会自动带上；未登录握手会被拒绝）。
所有数据帧均为 UTF-8 文本，内容为 JSON。URL 可带 `?since=<版本号>`：那是页面手上那份日志对应的
**回滚版本**（见下节），版本与镜像一致时服务端只回一帧 `history_same`，不回放任何行。

### 服务端 → 客户端

**1. 首次连接时推送历史快照**（随后才是实时事件）。快照分**三种帧**发出，使页面能一边收一边画，
且没有任何一帧是「整段历史」——WebSocket 消息是原子的，一个巨大的帧既无法分片渲染，也会让主线程
在解析+重建期间整段卡住（这正是超长会话停在 `Waiting for messages…` 的原因）：

```json
{ "type": "history_start", "version": 812, "tokens": 1234, "window": 131072, "busy": false, "markdown": true, "result": true, "count": 812 }
{ "type": "history_rows", "messages": [ { "role": "user", "content": "..." } ] }
{ "type": "history_rows", "messages": [ ... ] }
{ "type": "history_end" }
```

* `history_start` 是表头：`tokens`/`window` 用于顶部上下文用量徽标，`busy` 让运行中连上的页面也
  显示转圈指示，`markdown` / `result` 是当前的渲染开关与工具结果开关（重连的标签页据此与其它
  标签页或 CLI 的改动保持一致），`count` 是本次快照的行数，`version` 是这批行对应的**回滚版本**。
* `history_rows` 每帧一个**批次**：至多 200 行，或累计文本达到 256 KB 就提前切批（单行过大时自己
  成一批），因此单帧大小有上界（`internal/web/web.go` 的 `historyBatchRows` / `historyBatchBytes`）。
* `history_end` 收尾；之后的帧都是实时事件。收到 `history_start` 时页面**清空并重建**日志区
  （历史始终是全量快照），因此断线重连不会把同一条消息再显示一遍；每个批次用 DocumentFragment
  一次性插入，回放期间不读布局、不跑入场动画，Markdown 也在空闲切片里补渲染（见下节）。
* 服务端**注册连接与快照取景在同一把锁内**完成：快照期间到达的实时事件先扣在客户端队列里、
  等 `history_end` 之后按到达顺序补发，所以「快照 + 之后的事件」严格有序、恰好一次。

**1b. 没有任何变化时只回一帧 `history_same`**：镜像给可见回滚维护一个**版本号**，凡是改变行内容的
操作（追加一行、思考行继续变长、丢弃空的思考行、`/new` 清空、启动播种）都会让它 +1。页面把
「自己这份日志来自哪个版本」记下来，重连时用 `?since=<版本>` 报回；版本仍一致说明这段时间**一行都没变**，
服务端只回：

```json
{ "type": "history_same", "version": 812, "tokens": 1234, "window": 131072, "busy": false, "markdown": true, "result": true }
```

* 页面收到它**不动日志区**，只把表头里的状态（用量、`busy`、开关）应用上去——这正是手机停工后
  切回前台不刷新长会话的关键（否则每次回来都要重建整段回滚）。
* 它只出现在**真的重连**时（停工后回来、断线重连、刷新页面）：隐藏未满宽限期时页面不会断连，
  也就不会有这一步；而"到底重建不重建"只由重连时的版本是否仍一致决定。
* 比较版本与注册连接在同一把锁内完成，所以实时事件要么已经进了回滚（版本不同 → 照旧全量快照），
  要么作为实时帧发下来，**不会**被这个捷径吞掉。
* 版本不同（包括页面版本过旧、进程重启后的播种、`/new`）一律走完整快照；页面首次连接没有版本
  （不带 `?since=`），也走完整快照。

> `messages[].role` 取值与页面绘制的行一一对应：`user`、`assistant`、`reasoning`（模型
> 思考，斜体灰字）、`tool_call`、`tool_result`、`info`、`summary`、`error`、`interrupted`。
> `user` 行可以带 `attachments`：这条消息带走的文件的 `{name, type, url}` 列表（`url` 只在文件位于
> 上传目录时给出，页面据此把图片画成图片；见[附加文件](#附加文件apiupload)）。实时事件里的
> `attachments` 由镜像按同一规则转换后再广播，所以同一行无论实时到达还是回放都长一样。
> `summary` 是**压缩摘要行**（页面上是一条带虚线边框的醒目块），它标示上下文被截断的位置：
> 该位置之前的旧消息不再发给模型，取而代之的就是这一行摘要（见下方 `compacted` 事件）。
>
> 服务端在启动时就初始化自己的**内存回放缓冲**：先用当时的会话（如已恢复的历史）播种，
> 之后把事件总线上的每个事件追加进去（思考增量会合并成一条 `reasoning` 行）。因此网页
> 之后才打开、或刷新重连，都能看到完整的对话，包括思考、工具行与 info/error 标记，
> 且不受上下文压缩影响（与终端回滚一致）：旧消息不会被删掉，压缩只在切点追加一条摘要行。
> 而**恢复的会话**（进程重启后重新拉起）里，切点之前的消息本就不在，播种时摘要行会成为
> 日志区的第一行，表示此前的对话只以摘要形式保留。


**2. 实时事件**：字段与 Agent 事件一致。

```json
{ "type": "reasoning_delta", "text": "模型思考增量" }
{ "type": "assistant_delta", "text": "部分文本" }
{ "type": "assistant", "text": "完整回复" }
{ "type": "tool_call", "name": "exec_command", "args": "{\"command\":\"ls\"}" }
{ "type": "tool_result", "name": "exec_command", "text": "展示文本", "is_error": false }
{ "type": "info", "text": "..." }
{ "type": "compacted", "text": "context compressed: 20 -> 1 messages", "summary": "被压缩消息的累积摘要" }
{ "type": "interrupted", "text": "interrupted; the turn was stopped" }
{ "type": "error", "text": "..." }
{ "type": "usage", "tokens": 1234, "context_window": 131072 }
{ "type": "user", "text": "某客户端发送的消息", "source": "web" }
{ "type": "turn_done" }
{ "type": "settings", "markdown": true, "result": true }
```

* `compacted` 携带 `summary`：累计摘要（总结失败时退化为丢弃消息，此时它可能为空/未变）。
  CLI 与网页都在**截断处**显示它——CLI 先打印 `[info] context compressed: …` 再打印一个
  `[summary]` 块，网页在信息行之后追加一条 `summary` 行；网页的这条行同时写进回放缓冲，
  所以刷新/重连后摘要仍出现在同一个位置。
  箭头后的条数 = 摘要 + 保留策略留下的原始消息（`context.summarize_keep`，默认一条都不留，
  因此是 `1` —— 整段历史都被压缩时，剩下的那条是引擎补的 `[engine] Context summarized,
  continue.` 标记）。
  总结要调用模型（可能较慢），因此压缩**开始前**会先广播一条 `info`：
  `compacting context: summarizing N of M messages`，两端立刻显示「正在压缩」；没有可压缩
  内容时不广播任何事件（`/compact` 由命令处理方回复 `nothing to compress yet`）。
  服务商以「上下文超限」拒绝请求时的溢出恢复（回退本轮消息 → 摘要 → 重发）也在这条通路上：
  先一条 `info`（`context length exceeded: rolled back N message(s), compressing the context
  and retrying`），随后是同样的 `compacting context: …` 与 `summary` 行；被回退的行**不会**从
  日志与回放缓冲里删除，页面看到的就是「回退提示 + 摘要行」。

* `settings` 是**瞬时帧**（不进日志区）：服务端在网页侧开关（`/result`、`/markdown`）变化时广播，
  页面的命令栏据此刷新 on / off 状态；新页面从注入的配置、重连页面从 `history_start` 表头拿到同样的值。

* `usage` 在上下文增长的每个时点广播（回合开始、每次模型回复、每轮工具执行后），
  页面据此**实时**更新顶部上下文用量徽标（`tokens` 以接口返回的 `prompt_tokens` 为基准）。
* `user` 事件带 `source` 字段（`cli` / `web`），终端据此区分本地输入与网页输入。
* **`user` 事件在消息真正进入对话时才广播**（Agent 的 `drainSteering()` / `startSteeringTurn()`）：
  回合运行中提交的消息会先入队，等它所打断的那一轮结束后才进入上下文，事件也在**那一刻**才发出。
  因此各端画出的行、回放缓冲记录的行、以及模型上下文里的消息，顺序完全一致——刷新后的回放
  也就在同一位置。
* 提交那一刻的反馈由发送方自己给出（因为事件要等到真正发送时才到）：
  * 网页把这条消息**立刻画出来并标记为 pending**（`.user.pending`：虚线气泡 + 角色后缀
    `· pending`），且**本轮回复后续产生的行都插在它之前**（`placeRow` 用 `insertBefore` 插到
    pending 行之前），所以上一轮的 thinking/回复/工具行始终排在它前面；Agent 正式发送时该行
    **原地**变成普通消息（去掉 pending 标记，不新增行）。运行徽标另有 `12.3s · 1 queued` 计数，
    行转正式即递减；手机窄屏只留计数数字（`12.3s · 1`——`queued` 这个词会把顶栏撑到屏幕外，
    见[两种形态](#两种形态自适应)），完整句子在徽标的 `title` 里（与 CLI 排队时那句同义）。
  * CLI 把这条消息作为**灰色 `(pending)` 行画在提示区**（流式预览与提示行之间，按终端宽度折行、
    续行缩进，与输入框一致），正式发送时该行消失、正式行按事件位置打印（终端无法把已打印的行
    移到别处，所以正文行只有正式那一条）。一次性运行（`-p`）与行扫描（管道输入）等没有提示区的
    场合改为打印一行灰色 `(queued; it joins the conversation after the current reply)`。
* `reasoning_delta` 携带服务商暴露的模型思考（`reasoning_content` / `reasoning`）增量；
  页面用一个灰色 thinking 行流式渲染（按节奏重绘，见[省电](#省电移动端与隐藏页面)），
  收到后续非思考事件时定稿。
  `ui.markdown=true` 时该行与回答一样经 marked + DOMPurify 渲染为 Markdown，否则显示斜体纯文本。
  组装后的思考写入 assistant 消息（并以 `reasoning_content` 回传模型），同时进入服务端的
  内存回放缓冲，因此刷新/重连后的快照也会以 `reasoning` 行回放思考（CLI 的
  `/history` 仍只显示可见回答）。

> **Markdown 渲染在浏览器端完成**（`ui.markdown=true` 时）：页面加载内嵌的
> [marked](https://github.com/markedjs/marked)（GFM，支持表格）把消息渲染为 HTML（回答与
> 思考行一致），再用 [DOMPurify](https://github.com/cure53/DOMPurify) 净化后才写入
> `innerHTML`，因此不受服务端字段影响，协议保持与 Agent 事件一致。流式阶段按**节奏**重渲染当前
> 回复（见[省电](#省电移动端与隐藏页面)：可见桌面来一块画一块，可见手机最多每 100ms，后台每秒一次），
> 收到最终 `assistant` 时用完整文本定稿（同一行覆盖，不会重复出现两条回复）；
> `ui.markdown=false` 时不再调用库，直接用 `textContent` 显示纯文本。
>
> **公式走同一条管线**：`math.js` 先把 `$…$` / `$$…$$` 抽出来渲染成 MathML，marked 处理剩下的正文，
> 再把这些 MathML 放回 HTML、和正文一起过 DOMPurify（见[公式（MathML）](#公式mathml)）。因此
> `ui.markdown` 开着时公式才有排版，关掉时和别的 Markdown 一样按原文显示。
>
> **回放时 Markdown 走空闲切片**：重建快照的行数可能成千上万，逐行同步解析会把主线程占满
> （页面卡死、日志区停在 `Waiting for messages…`）。所以回放期间每行先画**纯文本**，再按
> 插入顺序在 `requestIdleCallback` 的空闲切片（每片约 8ms；不支持该 API 时退化为 16ms 的
> `setTimeout`）里就地升级为 Markdown；同一行只解析一次（取最新文本）。单个超过 20 万字符的
> 行不再做 Markdown，避免一整片被一行卡住。实时行（回合流式输出）仍然立即渲染 Markdown。

> 说明：`user` 事件会广播给所有客户端（包括发送者），因此页面无需本地回显；
> CLI 通过 `source` 字段区分来源，仅渲染非本终端（如网页）的输入。

### 客户端 → 服务端

发送一条用户消息或一条斜杠命令：

```json
{ "text": "帮我看看当前目录" }
{ "text": "/compact" }
{ "text": "这是什么？", "attachments": ["shot.png"] }
```

`attachments` 是**附件 id**（`/api/upload` 的返回值，见[附加文件](#附加文件apiupload)）；
它们随这条消息一起交给模型：服务端从 `.lightagent/uploads/` 读出文件，把内容作为用户消息的
多媒体载荷一起发出（形态见 [tools.md](tools.md#upload_media)）。**只有非命令消息会消费附件**：
以 `/` 开头的文本按命令处理，附件留在页面待发。

服务端先按**命令表**（`internal/slash`，与 CLI 同一份）解析以 `/` 开头的文本（全角 `／` 同样识别，
别名统一归一到主名，例如 `/interrupt` → `/stop`）：

| 命令 | 网页侧行为 |
|------|------------|
| `/help` `/?` | 列出命令表与网页说明；**只在网页里**（终端有自己的 `/help`） |
| `/new` | 清空会话，并清空网页日志区；回合运行中会拒绝，避免误点丢弃正在进行的对话 |
| `/save` | 通过 `SetSessionSaver` 回调落盘（程序把它接到 `cli.CLI.SaveSession`，与终端 `/save` 写同一份文件） |
| `/stop` `/interrupt` | 中断当前回合（与 CLI 共享） |
| `/compact` | 手动压缩上下文；回合运行中会拒绝 |
| `/history` `/context` | 上下文用量文案（与 CLI 共用同一份实现） |
| `/result` `/results` | 开关工具（exec）结果输出（与 CLI 共享同一开关），并广播 `settings` 帧 |
| `/markdown` | 切换**本页**的 Markdown 渲染并广播 `settings` 帧；终端的渲染开关属于终端，因此不做共享 |
| `/exit` `/quit` `/q` | 只提示「请在终端退出」：它会结束整个会话（含终端） |
| 其它 `/xxx` | 与 CLI 一致地报 `unknown command`，**不发给模型** |

共享状态的命令（`/new`、`/save`、`/stop`、`/compact`、`/history`、`/result`）的结果通过**事件总线**
广播，因此终端与所有网页看到同一条反馈；只属于当前页面的命令（上面的 `/help`、`/markdown`、
未知命令）只写进网页日志区，不会污染终端回滚。

不以 `/` 开头的文本调用 `Agent.SubmitFrom("web", ...)`：
* Agent 空闲 → 开启新回合；
* Agent 忙碌 → 作为 steering 插入当前回合。

发送时机不限制：任意客户端可在任意时刻发送，包括其它客户端/ CLI 正在运行回合时。

## 附加文件（`/api/upload`）

用户在输入框旁点 **📎** 选文件（可多选），页面立刻把文件 POST 到 `/api/upload`，
成功后在输入区上方出现一枚**附件标签**（文件名 + 类型/大小 + ✕）：

* **存哪**：工作目录下 `.lightagent/uploads/`，文件名就是**用户自己的文件名**（剥离路径与非法字符、
  限长；重名时在扩展名前加计数 `shot-2.png`）。服务端返回的 `id` 既是存储文件名，也是页面发回的消息字段。
* **随下一条消息发送**：`{"text": …, "attachments": [id, …]}`。服务端按 id 在**上传目录内**解析
  （只接受纯文件名，`../` 一类直接报错），读成多媒体载荷作为该用户消息的附件一起发给模型——
  因此**附件与那条提示词是同一条消息**，模型同时看到文本与文件。
  正文为空时服务端补一句 `(attached shot.png)` 作为该消息的文本，保证它仍是一条正常消息。
* **发送前可取消**：点标签上的 **✕** 只是把它从待发列表里去掉，同时向服务端发 `DELETE`
  删掉已上传的文件；发送成功后的标签自动消失（文件保留在上传目录里，因为它已经是对话的一部分）。
* **消息行显示它带的附件**：用户消息在正文下方列出这条消息带走的文件 —— 上传目录里的图片**直接画成图片**
  （点开在新标签页看原图），其它文件显示**文件名 + 类型**；图片取不回来（文件被删了）时 `<img>` 加载失败，
  自动退回文件名标签。行数据由服务端给出 `{name, type, url}`：只有上传目录里的文件带 `url`
  （`/api/media?id=…`），模型自己 `upload_media` 的任意本地文件只给名字 —— 镜像不会把一个它没存过的路径
  交给浏览器（见 `internal/web/pageAttachments`）。
* **只在配置了 `openai.media_types` 时才有这个按钮**（未配置时 `/api/upload` 直接 404）。
  选择器的 `accept` 就是配置的类型列表，服务端对类型与大小再校验一次（超限 413、类型不符 415，
  错误文案直接显示在标签上）；上限是 `tools.upload_media.max_bytes`（默认 20 MiB）。
* 页面始终知道当前能力：服务端把 `{enabled, types, accept, max_bytes}` 注入 `window.__LIGHTAGENT__.media`。
* 未被发送、也未被取消的文件会留在 `.lightagent/uploads/`（例如直接关了页面）。该目录可以手工清理，
  但**会话文件里存的是路径而不是内容**（见 [tools.md](tools.md#upload_media)）：清掉的文件在恢复会话时读不回来，
  那部分附件会退化成「名字 + 一句不可用」而不是原来的内容。

## 输入与显示

* 输入框：**Enter 换行、Ctrl+Enter 发送**（Shift+Enter 也是换行，可粘贴多行文本）；
  随内容自动增高（最多约 40% 视口高度，超出后内部滚动）。提示语在宽屏保持原文
  `Message lightagent…  (Ctrl+Enter = send)`，手机窄屏换成短形式 `Message…`
  （触屏键盘没有 Ctrl+Enter，长提示会被截断）；完整快捷键说明始终在输入框的 `title` 里。
* 顶部右侧徽标实时显示上下文用量：`ctx` + 百分比 + `tokens/window`（标签与 CLI 提示行的 `[ctx 12.3%]` 对齐，
  占用升高时变黄/变红）；手机窄屏只留百分比数字（`ctx` 与 token 数都隐藏），完整文案在徽标的 `title` 里。
* 标题栏左侧状态文字（`online` / `offline`）与右侧圆点反映 WebSocket 连接状态；
  断线时发送按钮禁用，并自动重连（退避 1.5s → 3s → … → 最多 60s，带抖动，握手成功即归零；
  重连前先向 `/api/session` 确认会话还有效，已失效则改为弹出登录对话框）。
  未登录（且配置了密码）时不会建立连接；**页面隐藏时不重连**（见[省电](#省电移动端与隐藏页面)）。
* **两种形态自适应**：整页是**两行网格**——**banner**（顶栏）独占第一行并横跨整宽，页面**唯一**的 logo 在这里
  （桌面端信息栏因此在它**下方**，而不是与它并列）；信息栏与内容区共享第二行（信息栏占第一列）；
  内容区本身仍是原来的那一列（顶栏、消息流、输入区），未做任何改动。
  **内容列是 `minmax(0, 1fr)`**（宽屏那版是 `var(--sidebar-w) minmax(0, 1fr)`），不是 `1fr`：`1fr` 轨道的
  下限取自网格项的 min-content，而顶栏那一排 nowrap 徽标撑不下时不肯收缩，于是把**整页**顶得比屏幕宽
  （`body` 裁掉溢出的右侧，右对齐的用户消息行——pending 行正是其中最新的一条——就落到屏幕右边外面）；
  下限写 0 后列宽永远是屏幕宽：顶栏挤自己，绝不挤正文。
  手机（窄屏）为单列——紧凑顶栏（上下文徽标只留百分比数字、**Sign out** 只留图标，
  与 🔊/⚙ 同为 36px 点触目标；徽标与图标按钮之间收到 4px，正好让 pending 时的运行徽标也放得下）+ 消息流 +
  底部输入区；
  信息栏折成**banner 下方的左侧抽屉**（顶边压住 banner 底边 1px、底色**不透明**，
  所以既不会有缝、正文也不会透出来；不覆盖 banner，drawer 打开后 logo 仍在，随时可点）：
  点 banner 左上的 **logo** 滑出（36px 点触热区，`aria-expanded` 与 `title` 随开合），
  收起方式——再点一次 logo、点内容区上的遮罩、按 **Esc**（上面有面板时由面板接管这个键）、
  或在抽屉里点下任一动作（命令 / **Edit config.json** / **Voice settings**）；
  焦点在打开时进入抽屉本身（`tabindex="-1"`）、收起后回到 logo。
  开合是 **160ms 的一次快速滑动**（`visibility` 延迟到滑动结束才切换，因此收起时会完整滑出去；
  系统开启「减弱动态效果」时不动）。抽屉宽 `min(292px, 86vw)`，遮罩只盖第二行（banner 保持可交互）；
  跨 1000px 断点（旋转、改窗口大小）自动回落为关闭；宽屏下 logo 只是装饰（不进 Tab 顺序、指针穿透）。
  桌面（宽屏 ≥1000px）在 banner 下方展开固定信息栏：上下文进度条（随占用变黄/变红）、
  **Commands 命令栏**（默认只列 `primary` 的那些命令，其余折叠在标题后，点击标题展开/收起；
  点击即执行；`/result` 与 `/markdown` 显示 on / off 状态，点击切换另一状态）、
  配置编辑器入口与 **Read aloud** 朗读卡片（自带的启用开关 + **Voice settings** 面板入口；
  页头 **🔊** 打开同一个面板，手机端也能用），
  右侧为聊天主区（日志区右下角悬浮**上一条用户消息**与**最新消息**两个按钮，见下文）。
* 布局用 `100dvh` 动态视口高度 + 安全区（含顶部刘海与横屏左右内边距）适配手机；
  不使用 `position:fixed`，输入区始终可见；内容列居中且最宽 920px；点触目标不小于 44px。
* 回合运行中顶部显示转圈指示，输入框右侧出现 **Stop** 按钮：点击等同于发送 `/stop`，
  中断当前模型调用或工具调用；中断事件（`interrupted`）与工具反馈 `interrupted by user`
  会和其它事件一样广播给所有客户端。中断落在**任何工具调用开始之前**时：已经流出的**正文**保留
  （流式的那条 `assistant` 行由 `assistant` 事件定稿，与 CLI 一致），其中携带的 tool 调用全部
  丢弃；正文为空（只有思考 / tool 调用）时连这条消息也不保留。中断落在**工具调用已经开始之后**
  时：正在执行的那个调用照常返回真实结果，其后未开始的调用各记一条 `interrupted by user`
  （见 [architecture.md](architecture.md#agent-回合循环)）。这些记录只进历史，随**下一条用户
  消息**一起发出。
* 转圈指示旁是**本回合用时**，格式与 CLI 提示符一致（`busyElapsedLocked`）：不足一分钟
  显示到 0.1 秒（`12.3s`），之后 `1m05s`、`1h02m`。计时随转圈一起开始、可见桌面每 100ms 刷新
  （与 CLI 的动画节奏相同；可见手机与后台页面 1 秒一跳，见[省电](#省电移动端与隐藏页面)），
  `turn_done`/中断/断线即清零；运行中的 steering 消息不重启计时，
  但计时从**本页**看到回合开始算起，因此运行中刷新或重连会从零重新计时；
  手机停工（隐藏满 1 分钟）后计时器停掉，回来由快照重新报出状态。
  转圈动画**不受**“减弱动态效果”偏好影响（该偏好只关闭消息行的入场动画）——它是运行中的
  唯一提示，停止转圈看起来像卡死。
* 工具调用行（`tool_call`）与 CLI 一致：**函数名单独一行高亮**（黄色加粗），参数**不缩进**地
  逐条列出——单行值紧跟参数名（`参数名 - 值`），多行值则参数名单独一行、值从下一行开始；
  参数名为青色加粗、分隔符与值为灰色（与 CLI 调色板对齐）。值用原始内容（字符串去掉引号，
  嵌套数组/对象为紧凑 JSON），解析失败时回退为原始文本。
* 工具（exec）结果按纯文本展示，保留换行；用 `/result off` 可隐藏。
* **消息行的顺序始终与提交顺序一致**：回合运行中提交的消息（steering）先入队，Agent 在
  `drainSteering()` 把它并入上下文时才广播 `user` 事件，因此这条消息的**正式行**恰好落在它所
  打断的那条回复（含该轮的工具行）之后，本轮剩余的增量都在它之前——不会出现"消息夹在思考与
  回复之间"或"直接跟在上一条消息之后"的错位（回放缓冲记录的就是这个事件，刷新后位置相同）。
  在它正式发送之前，页面把这条消息画成 **pending 行**（虚线气泡 + `· pending`），本轮后续
  行都插在它之上，所以即使回复还在流式输出，"上一轮的反馈在前、插入的消息在后"也一直成立。
* **滚动跟随由“读者意图”决定，而不是几何距离**：日志区只在**跟随中**（`following`）时才把新输出
  拉到底部。流式输出每帧都在把底部推远，所以只按“离底部 ≤8px”判断时，一次贴底就足以抵消读者的上翻
  ——这正是“怎么都拉不上去”的原因。因此读者自己的上翻动作会**立即**熄掉跟随：滚轮向上
  （`deltaY < 0`）、手指向下拖动内容（`touchmove`）、PageUp/Home/ArrowUp/Shift+Space（发生在输入框与
  表单控件里的按键不算）。这些探测都在浏览器应用滚动之前，并且 `pinBottom` 在写入那一帧**再检查一次**
  `following`，所以一帧内已经排队的贴底写入也会让位给手势。停止跟随后输出照常追加在下方，视图停在原处。
  **恢复跟随**只有一条路：滚到最末端（读者自己滚到底、发送消息、或点“最新”按钮）；滚动条拖动没有
  滚轮/触摸事件，由 `scroll` 事件按方向补上（向上移动 → 停跟随；向下落回底部 8px 带内 → 恢复跟随，
  刚停跟随的 400ms 内不这样判读，以免把同一次动作读成“想往下”）。窗口尺寸变化（手机键盘弹出等）
  会让仍在跟随的视图重新贴底；反过来，`following` 只表达意图，所以日志**上方**内容变高（图片加载、
  回放行升级为 markdown）把视图挤离底部时，下一行输出就会把它拉回来，不会像“只按几何判断”那样卡住。
  * **底部要在同一任务里补写**：让行变高的那次改动（流式重绘、新行、pending 行、附件进入行内）改完
    DOM 立刻 `keepBottom()` 写底部——但只对**页面自己还握着滚动位置**的读者：`pageScrollTop` 记着页面
    最后一次写下的 `scrollTop`，读者一动手这个值就对不上（而那个手势的 `scroll` 事件可能还没派发）。
    判据**不能**用“离底部 1px 以内”：软键盘、resize、亚像素都会留下几像素，而只要留下几像素，之后每个
    分片就退回下一帧的 `pinBottom` 写——实测那种情况 `gap` 在 `0↔55px` 间反复 41 次、pending 行抖动
    **115px**；改用“位置是否还是页面自己写的”后同一场景 `gap` 只从 4px 一次性归零。若一律等下一帧才写，
    则连正常贴底时也会画出一帧“底部落后”（实测每个流式分片落后 22–80px），pending 气泡被推下去再弹
    回来，看起来就是上下抖动。读者不在底部（自己翻上去了）仍走 `pinBottom` 的下一帧写，并照上面那样
    让位给手势；读者滚回末端时 `onLogScroll` 记下新位置，页面重新接管。
  * **贴底要写准，而行高必须是整像素**：`writeBottom` 不按算术算目标（`scrollHeight` 与 `clientHeight`
    都是取整的整数），而是**量出内容底边与盒子底边的差再补**（`contentOffset()`，两趟），把内容底边
    精确落在盒子底边上。**但滚动位置只能落在整像素上**（实测：写 `scrollTop = 6879.7` 读回 `6880`），
    所以只要内容总高度带小数，底边位置就会随每次分片的小数部分漂移——`line-height:1.6` 在 14px 字号下
    正是 **22.4px**：实测 pending 行连同气泡每帧上下浮动 **0.97px**（手机 DPR 2~3 上就是 1~3 个设备
    像素，肉眼可见的“抖动”）。因此日志区（`#log`）以及其间自成行高的元素（`.role` 16px、工具行 20px、
    thinking 行 21px、附件 19px、标题 25/22/20/18px）统一改用**整像素行高**（见 app.css）：内容高度
    变成整数像素后，底边正好落在写入的位置，实测同一场景 pending 行的位移 **0**、方向反转 **0** 次。
  * 日志区关掉浏览器自带的**滚动锚定**（`#log { overflow-anchor:none }`）：锚定会在上方内容变高时
    让视口顶部的元素保持不动，方向与页面的贴底写入相反，两者交替同样会让底部那一行抖。
  * **视口本身变了也要在同一任务里贴底**：手机的**地址栏收缩/展开**、软键盘弹出收起都会让视口高度
    连续变化（`window.resize` 与 `visualViewport.resize` 都监听）。跟随中就在同一任务里 `writeBottom()`
    把内容底边重新对到盒子底边——若像以前那样交给下一帧的 `pinBottom`，视口变化的那一帧就会画出
    “底部错位 60px”（实测地址栏动画期间 pending 行摆动 **112px、方向反转 39 次**；改成同任务写之后，
    同一动画里对齐误差**恒 0**、位置逐帧跟随视口 2px 平移）。桌面窗口尺寸不变，所以从来没有这一项。
* **日志区右下角两个悬浮按钮**：**Previous**（上一条用户消息）与 **Latest**（最新消息）。
  Previous 回到**起点位于视口上沿之上的最新一条用户消息**（`log.children` 里本页发出的 pending 行也算），
  把视口顶在它上方 10px 处，并**停止自动滚动**；上面没有更多消息时什么都不做；再次点击继续往上走一条
  （上一次落点的那行被排除，所以不受取整影响）。Latest 贴底并**恢复跟随**。
  **已经在底部（跟随中）时 Latest 淡出**（`.off` 只改透明度与可见性、**保留占位**，所以按钮组不会跳位），
  只有真被翻上去过才提供回到底部的入口；日志区为空时两个按钮都不显示（`#log:empty ~ .jump`）。
* **两个按钮的样子**：上下竖排（上 = Previous、下 = Latest），贴在**屏幕右边**（桌面 `right:16px`，
  不再对齐消息列；手机 `max(12px, env(safe-area-inset-right))`，窄屏下本来就是屏幕边），离底边留一点距离
  （桌面 `bottom:20px`、手机 `16px`）。图标是**一条横杠 + 一个尖角**（`|←` / `→|` 的竖排版，不是两根
  光秃秃的箭头）。桌面为**细长胶囊**（高 34px、圆角 999px、**图标 + 文字**居中），
  手机为 **40px 圆形按钮**、只留图标（文字隐藏）。默认**半透明**（桌面与手机同一档
  `rgba(18,26,38,.4)` + 背景模糊，下面的正文看得见），**鼠标移上去才变不透明**
  （`@media (hover:hover)` —— 触屏不会有"粘住的 hover"）；
  出现/消失走透明度过渡（`transition: opacity/visibility .24s`），不是忽然 display 切换；
  手机上再关掉点按高亮（`-webkit-tap-highlight-color:transparent`）与 `:focus-visible` 边框，按过不留高亮。
  它们悬浮在日志区自己的盒子（`.stream`）里，因此同样不使用 `position:fixed`。
* **重连重建是分批的**：快照按批次到达，每批用 DocumentFragment 一次性插入，回放期间
  **不读布局、不跑入场动画**（`#log.replaying .row` 关掉动画），结束（`history_end`）时贴底一次
  ——等同刷新页面的最终状态。因此重建一段很长的对话只会产生「每批一次重排」，而不是
  「每行一次强制布局 + 一次滚动写入」。

## 公式（MathML）

回复里的 LaTeX 公式（`$…$` 行内、`$$…$$` 独立成行）渲染为 **MathML**，由浏览器自带的数学排版引擎绘制：

* **不引入 KaTeX / MathJax**：前者要额外内嵌约 1 MB 字体，后者更大；而 MathML 的根式、分数、上下标、
  大算符都是引擎能力，**零新增资源**、随页面缩放、文字可选中、读屏软件也能读，引擎不支持时还会
  退化成公式内容的文字（公式不会消失）。`math.js` 约 1150 行 / 53 KB、无依赖，随二进制内嵌、无构建步骤。
* **覆盖的子集**（约 350 个命令）：希腊字母与常用关系 / 运算 / 箭头符（`\leq` `\geq` `\leg` `\greq`
  `\nleq` `\prec` `\sqsubseteq` `\asymp` `\vDash` …）、集合与二元运算（`\cup` `\cap` `\uplus` `\circ`
  `\oplus` `\otimes` `\triangle` …）、箭头（`\to` `\mapsto` `\hookrightarrow` `\Longrightarrow` …）、
  `\frac` / `\cfrac` / `\binom` / `\sqrt[n]` / `^` `_`、重音与上下括号（`\overline` `\hat` `\vec`
  `\overbrace` `\underbrace` `\overrightarrow` …）、`\text{}`（内容原样直立）、`\quad` `\,` `\;` 等空白、
  `\left(\right)` 与 `\big` 系列定界符、`\sum` / `\prod` / `\int` / `\iiiint` / `\oint` 等大算符
  （**行间公式**把上下限放在符号上下、行内与积分始终放在右侧，与 TeX 一致）、`\Box` / `\dagger` /
  `\pmod{n}` 这类常用写法，以及 `\mathbf` / `\mathbb` / `\textbf` 等字体命令。
* **排版开关不显示**：`\displaystyle` / `\textstyle` / `\limits` / `\nolimits` / `\mathstrut` /
  `\phantom` / `\notag` 这些只说“怎么排”的命令直接丢弃（不会把名字打进公式），而 `\sum\limits_{i=1}^{n}`
  这类写法仍然把上下限接在算符上。
* **括号带着上下标**：`(x_i-\mu)^2`、`\left(\frac{n}{e}\right)^n` 里的指数落在**整个括号组**上——成对
  的定界符合成一个 MathML 组，两侧因此同时被拉到内容高度。否则 MathML 只按同级内容定高，开括号会被
  指数撑高、闭括号还是原大小，看起来就像上下标挂错了地方。
* **多行公式排成表格**：`\\` 分行、`&` 分列，`aligned` / `align` / `gather` / `split` / `cases` /
  `matrix` / `pmatrix` / `bmatrix` / `Bmatrix` / `vmatrix` / `Vmatrix` / `array` 都排成 `<mtable>`
  （`aligned` 按 TeX 规则在 `&` 处右 / 左交替对齐，`cases` 左侧带 `{`，`array` 按自己的列格式 `lcr`
  对齐）；没有环境的裸 `\\`（如 `$$a \\ c$$`）排成单列表格。
* **字体**：`\mathbf` / `\mathbb` 等命令同时写 `mathvariant` 属性与页面样式类——MathML Core 已把
  `mathvariant` 换成 CSS，Chromium 因此读类（`\mathbf` 真的加粗、`\mathbb{R}` 直接换成 ℝ 这类双线
  字符），仍实现该属性的引擎则读属性。
* **公式不会被 Markdown 吃掉**：抽取时跳过围栏代码与行内代码（那里的 `$` 保持为代码），`\$` 是
  转义美元符，而 `_` `*` `\%` `\{` `\;` 不再触发强调或转义——`x_i^2` 得到的是 x 的上下标。
* **不会被误判**：单独的 `$`、价格（`$5 and $6`、`US$7`、紧贴单词的 `US$7 cheap`、纯数字的 `x$5$`）都
  保持原文——行内公式要求 `$` 与内容之间没有空格、内容里没有第二个孤立的 `$`，含空格的正文还必须带
  反斜杠或运算符这类数学记号；反过来，紧贴单词的公式（`Cauchy$|x|\le 1$`）现在也能识别，而未闭合的
  `$` 不会再吞掉下一行的文字（闭合符优先在**同一行**里找）。
* **流式期间**：`$$` 的闭合还没到时不渲染（按原文显示），最终一次重绘时才转成 MathML，与表格、
  代码块的流式表现一致。
* **不支持的写法**退化而不是报错：不认识的环境（`\begin{foo}…\end{foo}`）只丢掉命令本身、内容照常
  排出；未知命令按直立文字显示其名字（`\foo` → `foo`）；`{…}` 仍是分组（不显示花括号，和 TeX 一致，
  要显示花括号请写 `\{…\}`）；矩阵环境里的 `\hline` 与列分隔线不画。
* 渲染结果与正文一起过 DOMPurify（MathML 的标签与属性都在它的默认允许清单内），页面既不放行别的
  标记，也不需要额外白名单；只有表格的 `columnalign` 要显式加回——DOMPurify 的 MathML 属性表把它
  拼成了 `columnsalign`，所以 `app.js` 的净化调用传 `ADD_ATTR: ['columnalign']`。

## 复制消息

每条**用户消息**与每条**助手回复**的**角色标签旁**都有一个**透明的复制图标**——助手回复在 `agent`
**右边**、用户消息在 `you` **左边**（镜像对称，两者都朝消息内侧、距标签 6px），点开后从三个口味里选
一个，整条消息进剪贴板：

* **Markdown**：消息**写入时的原文**（模型写的 markdown 源码）——页面上渲染成什么样都不影响，
  重连后由快照回放出来的旧消息同样保留原文；
* **HTML**：渲染后的块（粘进富文本编辑器/邮件里保留标题、列表、表格与代码块），**同时带上纯文本
  口味**（粘到纯文本编辑器里不会出现 `**` 之类的标记）；页面关掉 `/markdown` 时用同一套
  marked + DOMPurify 现场渲染，库不可用时退化为转义文本，因此这个口味不会为空；
* **Text**：屏幕上读到的样子（渲染行的文本，标记已去掉）。

细节：

* **平时完全看不见，也不占布局**：图标挂在角色行里一个**零尺寸的 flex 项**上（按钮从中浮出，
  `opacity:0` + `pointer-events:none` + `scale(.8)`），所以角色行的高度与宽度一个字都不变，
  消息不会被挤动，不可见时鼠标事件穿透、不会吞掉点击；显现时有一个极短的放大淡入。
* **怎么显现**：桌面端鼠标移上该行即显现（键盘 Tab 到图标同样显现，`:focus-within`）；
  **触屏没有 hover**，**长按该条消息**约 0.45 秒显现（手指移动超过 10px 即取消，所以滚动、
  拖选文本不会误触发），**轻点消息**也能显现/收起，点别处即收起。跟随手势的
  `touchstart`/`touchmove` 用 passive 监听（不干扰浏览器自己的滚动与选择），长按成立时
  `touchend` 会丢弃那次合成的点击——否则它会把刚显现的图标又切换掉。
* **位置与对称**：助手回复是 `● agent ⧉`（图标在标签右侧 6px）；用户消息是 `⧉ ● you`
  （图标在角色标记左侧 6px，二者都朝消息内侧）。图标垂直居中于角色行，**下端不超过正文首行**
  （桌面 24px 的按钮正好落在角色行那条带里）。
* 手机宽度下点触目标是 32×32px，字形 15px，仍居中于角色行，因此也不会压住正文；
  回放期间（`#log.replaying`）同样如此。
* **菜单是三口味共用的一个图标小面板**（桌面 102×36px、手机 120×40px）：**只有图标、没有文字**
  （Markdown `M↓` / HTML `</>` / 纯文本三行线；口味名称在 `title` 工具提示与 `aria-label` 里）；
  `prefers-reduced-motion: reduce` 时只保留面板、不做位移。点别处、滚动日志、改变窗口大小、按
  **Esc** 都会收起；会话切换（快照重建）时也收起。复制成功后菜单下方浮出一行小提示 **`copied`**
  （失败时是 `copy failed`，完整提示在它的 `title` 里）。
* **写剪贴板有两条路**：安全上下文（`https://`、`localhost`/`127.0.0.1`）走异步 Clipboard API
  （`navigator.clipboard.write`，可一次写入 `text/html` + `text/plain`）；局域网里最常见的**明文
  HTTP**（`http://192.168.x.x:8080`，手机就是这样打开的）没有这个 API，于是自动退化为「离屏
  textarea 选中 + `execCommand('copy')`」，HTML 口味由 `copy` 事件写入——所以手机在明文 HTTP 下
  同样可用。两条路都在点击事件的同一个任务里启动（iOS Safari 的要求），复制后还原用户原来的选区。
* 只有**消息行**（`user` / `assistant`，含 pending 行）带这个图标：工具调用、工具结果、info 等行
  不属于「消息与回复」。

## 朗读（浏览器 TTS）

页面可以把 Agent 的输出**读出来**：用的是浏览器自带的语音合成（Chrome/Edge 的 Web Speech API，
即 `window.speechSynthesis` + `SpeechSynthesisUtterance`），文字完全在本地合成，不联网、不经过服务端，
也不写入任何会话文件。

* **启用开关：默认关闭**。面板顶部的 **Read aloud** 开关与桌面侧栏 **Read aloud** 卡片里的
  **Speak the agent's output** 是同一个开关（两处同步）；关闭会立即静音并清空朗读队列。
* **入口**：页头 **🔊** 按钮，或侧栏卡片的 **Voice settings**，打开设置面板（语言/语音、朗读内容、
  Test / Stop）。开启朗读后这两个入口都会高亮——这是面板之外唯一的提示，表示这个页面会说话。
* **不支持则不启用**：浏览器没有 Web Speech API（或没有 `SpeechSynthesisUtterance`）时开关**强制为关**
  且控件全部禁用，面板底部直接说明原因；已存储的偏好**不会被改写**，换到支持的浏览器后仍然生效。
* **设置存在浏览器里**（`localStorage` 的 `lightagent.tts`，与登录“记住我”的摘要同一个存放处）：
  刷新、重开浏览器都还在，且**只影响当前浏览器**（手机与桌面可以各自不同，互不打扰）。
  也正因如此，它**不在 `config.json` 里**，服务端与其它浏览器都看不到这份设置。
* **语言/语音**：下拉框按语言分组列出**当前浏览器已安装的语音**（例如 `zh-CN` 下的 “Google 普通话”），
  在线语音标注 `(online)`；选“System default”则交给浏览器决定。语音列表是异步填充的
  （`voiceschanged`），尚未就绪时先列出常用语言标签（`zh-CN`、`en-US` …），此时只设语言、由浏览器挑语音；
  选择按 **voiceURI 记忆**，该语音不存在时退化为“同语言的任意语音”，再退化为浏览器默认。
  **Test** 按钮用当前选择读一句样例，便于确认声音是否合适。
* **朗读内容**（两种方式二选一）：
  * **Final summary of the round**：每回合只读一次——回合结束时（`turn_done`）读**该回合最后一条
    助手消息的文本**，也就是这一轮的最终结论；中间的过程文本、工具调用都不读。
  * **Only what is ticked below**：把对话行**实时**读出来，三个勾选项各自独立：
    * **Thinking process**：思考块（`reasoning_delta`）在**定稿时**整段读出（与页面上的 thinking 行
      同样的规则：任何非思考事件即结束该块）；
    * **Tool calls (tool name)**：每次工具调用只读**函数名**（参数不读，留给眼睛）；
    * **Text feedback (reply text)**：每条**定稿的**助手消息文本读出（中间过程文本也会读）。
* **停止与打断**：面板的 **Stop** 立即清空队列并打断正在读的内容；发送新消息（新回合或 steering）、
  `/stop` 中断回合、或关掉朗读开关时同样会静音；重连/`/new` 重建日志区时（`history_start`）会清空缓冲并静音。
* **不会朗读历史**：页面重放快照时**不经过**朗读（`app.js` 只在非重放事件上调用 `TTS.event`），
  所以刷新页面不会把整段对话念一遍。
* **文本预处理**：先用 Markdown 的纯文本化（去掉标题/列表/引用标记，链接只留文字，删除围栏代码块，
  表格竖线变空格，强调标记去掉而 `max_lines` 这类下划线变空格），再按句切成**≤180 字符**的分片逐条合成
  （长句在空格处断开）：一是部分 Chrome 语音会截断过长的整段文本，二是分片才能干净地被 Stop 打断。
  队列上限 60 片，超出时丢弃最旧的分片，保证朗读大致跟得上屏幕。
* **限制**：需要浏览器支持 Web Speech API（Chrome/Edge/Safari 的现代版本可以；不支持时面板直接说明），
  声音取自操作系统/浏览器安装的语音包；朗读是**纯前端**能力，CLI 侧不受影响。

## 省电（移动端与隐藏页面）

Agent 在服务端运行，页面只是镜像，所以"没人看"时页面没有必须保持最新的东西——但放松到什么程度
按设备区分：**桌面**（有电源、常切标签页）照常保持连接与回放，只把重绘降到每秒一次；
**手机**先给 **60 秒宽限**（切个标签、屏幕暗一下都很常见），60 秒仍不可见才**停工**，
回来时用一次完整快照把日志区重建（与刷新页面同一条路径，`history_start…history_end`），
不存在"补播窗口期"。

* **后台节流**（可见性变化即生效，`visibilitychange`）：后台时流式行与运行徽标都变成**每秒一次**
  的节奏（`renderIntervalMs`/`turnTickMs` 读可见性），socket 与日志区照常更新，所以切回来立刻就是
  最新的；桌面不会停工。
* **手机停工**（隐藏满 60s，`HIDDEN_GRACE_MS_PHONE`）：停掉本回合计时器、**主动关闭 WebSocket**
  （服务端 30s 一次的空闲 ping 会把睡着的手机 radio 唤醒）、并给 `<html>` 加 `data-idle`
  （`data-idle` 下唯一的无限动画——运行徽标的转圈——被 `animation-play-state:paused` 停住）。
  变可见时移除该属性并重新拨号（退避计数清零）：**停工期间一行都没变时，服务端只回 `history_same`，
  日志区原地保留、既不重建也不重绘**（见 [WebSocket 协议](#服务端--客户端) 的「1b」），
  停工期间有新消息才用完整快照重建；两种情况下用量与"是否正在运行"都由回复一并带回。
  （口径要注意区分：隐藏**未满** 60s 时页面根本没有断连——socket 一直活着、事件照收、
  日志照更新（后台 1s 节奏），切回前台只是恢复全速渲染与计时，不存在"回来要刷新"这回事。
  刷新与否只在**真的发生重连**时才有意义：停工后回来、断线重连、刷新页面。）
  等待中的 Markdown 空闲升级同样保留——它属于日志区，而页面停下时没有任何定时器在跑。
  `pagehide`/`pageshow` 与 `freeze`/`resume`（Safari 的 bfcache 交接、Chrome 丢弃标签页）表示页面
  本身要走了，**任何设备**都会立即停工。
* **渲染节奏**：实时流式行是"整行重新解析 Markdown"，所以按"看得见的最快"来定：
  * 可见的**桌面**：来一块画一块（间隔 0，同一批到达的增量仍合并成一次重绘）；
  * 可见的**手机**：最多每 100ms 重绘一次（`RENDER_LIVE_PHONE_MS`，整行重解析在手机上贵得多，
    而十分之一秒在流式文本里看不出来）；
  * **后台**（未停工）：每秒一次（`RENDER_HIDDEN_MS`）。
  thinking 行与回答都在**定稿时**各做一次完整重绘，所以挂起的中间帧不会留下未渲染的文本。
* **运行徽标计时器**：可见桌面沿用终端的 100ms（与 CLI 动画节奏相同），手机与后台都是 1 秒一跳
  （十分之一秒在小屏上没有信息量，而每一跳都要写 DOM）；可见性变化时正在走的时钟会就地换档
  （`restartTurnTimer`）。
* **日志区的滚动写入**合并进一次 `requestAnimationFrame`（一帧内可能追加多行、流式行还会重绘，
  而每次写 `scrollTop` 都会触发一次布局）。
* **帧数**：`reasoning_delta` / `assistant_delta` 是唯一的高频流量，同一流上连续的增量在
  **50ms 窗口**内合并成一帧再发给各客户端（上限 64KB；遇到其它事件或窗口到期立即发出，顺序不变）。
  手机上帧数基本等于 radio 唤醒次数，所以这是除"手机停工"外最直接的省电项。回滚缓冲不受影响：
  每个增量仍按原样记录，晚连上的页面回放出的行完全一致；连接注册时会先把待发合帧送出，
  以免快照与其后的实时帧把同一段文本画两遍。
* **空闲心跳**：服务端的 30s ping 只在"距上次出站帧 ≥ 30s"时才发（刚推过帧的连接显然是活的），
  不再定时打扰一个安静但健康的连接。

## 连接维护

* 页面在连接断开后自动重连，退避从 1.5s 起翻倍（最多 60s，带 ±25% 抖动，抖动值也不越过上限），
  握手成功即归零；**已停工的页面不重连**，重新可见时才拨号（见[省电](#省电移动端与隐藏页面)），
  后台但未停工的页面照常重连。重连时页面用 `?since=<版本>` 报出自己那份日志的版本，
  因此"没有新消息"的重连只回 `history_same`（日志区不重建，见上节）。
  断线发生在快照回放中途时，页面会丢弃这次半成品回放，
  下一条连接用完整快照重建（因此日志区可能短暂只有一部分行，属正常）。
* **重启**（见[重启](#重启apirestart)）走的就是这条路径：面板确认重启后把页头状态改成 `restarting…` 并把退避清零，
  旧进程退出、新进程绑定同一地址，页面通常 1~2 秒内重连成功并回放恢复后的会话；新进程起不来时提示的是 `offline`，
  而页面会一直按退避重试（此时可在终端里看到失败原因）。
* **每个连接有自己的发送队列与写协程**（`internal/web/client.go`）：注册连接与取快照在 `s.mu`
  内完成，**但序列化与 socket 写入都在锁外、在该连接自己的协程里**。所以一个
  卡住不读的浏览器（休眠的笔记本、断点停住的调试器）不会拖住镜像：不会阻塞其它页面、
  不会阻塞 Agent 事件、也不会阻塞 `/`、`/ws` 等请求。
* 队列积压超过 32 MB（实时帧，快照本身由回滚量决定）时该连接被关闭，页面重连后重新取快照。
* 写操作串行化并带 15s 写超时；写失败的连接立即关闭（读循环随即注销它），不会留下半个帧。
* 连接**空闲 30s**（这段时间内没有推过任何帧）才发一个 ping（浏览器自动回 pong），
  以便发现悄悄消失的页面；刚推过帧的连接显然是活的，不再打扰。服务端也会应答浏览器发来的
  ping，并在收到 close 帧时正常收尾。

## 实现说明

`internal/web/ws.go` 用标准库实现了最小可用的 RFC6455：

* 握手：计算 `Sec-WebSocket-Accept = base64(sha1(key + GUID))`，通过 `http.Hijacker`
  接管连接并返回 `101 Switching Protocols`。
* 帧：支持 7/16/64 位长度、客户端掩码解码、分片重组；处理 ping/pong/close 控制帧。
* 入站单帧上限 8 MB。**出站按批次分帧**（见 `historyBatchRows` / `historyBatchBytes`），
  避免出现浏览器无法分片处理的巨大消息。
